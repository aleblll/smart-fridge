# **Архитектура автономной агентной разработки на базе Gemini Flash Thinking и графовой базы знаний Obsidian**

Построение детерминированного цикла разработки коммерческого программного обеспечения силами автономных языковых моделей требует отказа от парадигмы универсального агента в пользу стратифицированной многоагентной системы, где локальный репозиторий заметок Obsidian функционирует как графовый единый источник правды (Single Source of Truth, SSOT). Ключевой инженерный барьер автономной разработки — деградация контекста и накопление галлюцинаций при разрастании кодовой базы — устраняется разделением когнитивной нагрузки между специализированными профилями модели Gemini Flash с динамическим управлением бюджетом рассуждений (High, Medium и Low Thinking). Модели не модифицируют файлы наугад: они запрашивают изолированные контракты и фиксируют изменения через стандартизированный интерфейс Model Context Protocol (MCP), гарантируя абсолютную воспроизводимость каждого шага.

Основополагающий принцип архитектуры заключается в замене монолитной загрузки контекста протоколом динамической доставки Just-In-Time (JIT). Вместо исчерпания контекстного окна полным дампом проектной документации агенты обращаются к графу знаний Obsidian через AST-индексаторы метаданных, получая исключительно нормализованные архитектурные решения (ADR), DDL-схемы реляционной базы данных и OpenAPI-спецификации, привязанные к конкретной задаче спринта. Замкнутость среды обеспечивается транзакционным контролем: задачи переводятся в терминальные статусы только после прохождения автоматизированного контура самопроверки, подтверждающего прохождение юнит-тестов, отсутствие дрифта схемы в PostgreSQL и валидность типов.

В результате формируется самодостаточная среда разработки: агент-архитектор высокого уровня рассуждения декомпозирует требования в формальные спецификации внутри хранилища Obsidian, агент-разработчик средней мощности синтезирует код и тесты по методологии TDD, а низкозатратная модель форматирует кодовую базу и синхронизирует служебные реестры. Подобная топология снижает накладные расходы на токены более чем на 80% по сравнению с неструктурированными агентными запусками и исключает архитектурный дрифт в коммерческих проектах.

## **Архитектура хранилища Obsidian как ядра проектной спецификации**

Локальное хранилище Obsidian представляет собой файловую систему слабосвязанных плоских текстовых документов в формате Markdown, обогащенных синтаксисом междокументных ссылок (\[\[wikilinks\]\]) и структурированными блоками свойств YAML Frontmatter. В контексте агентной разработки vault выступает в роли реляционно-графовой базы данных, в которой плагин Dataview и внешние MCP-парсеры выполняют детерминированную навигацию по сущностям проекта без необходимости поддержания внешней СУБД для метаданных.

## **Контекст и проблематика**

Обработка транзакций списания требует гарантированной доставки событий во внешние аналитические сервисы без блокировки основного HTTP-потока.

## **Рассмотренные альтернативы**

> 1. Прямой вызов вебхуков из контекста веб\-сервера.  
> 2. Использование брокера сообщений RabbitMQ.  
> 3. Потоковая передача через Redis Streams с группами потребителей.

## **Решение**

Использовать Redis Streams с постоянными группами потребителей (Consumer Groups) и подтверждением обработки через XACK.

## **Последствия**

> * Положительные: изоляция latency HTTP-эндпоинтов, возможность повторного воспроизведения событий из истории стрима.  
> * Отрицательные: необходимость ручного мониторинга нераспределенных сообщений в Pending Entries List (PEL).

## **Градация моделей и вычислительная экономика рассуждений**

Эффективность агентной системы зависит от прецизионной аллокации вычислительных ресурсов рассуждения. Архитектура Gemini Flash поддерживает параметризацию процесса мышления: параметр thinking\_budget (от 0 до 24 576 токенов в Gemini 2.5 Flash) и его развитие в виде перечисления thinking\_level (minimal, low, medium, high в Gemini 3 Flash) позволяют регулировать объем генерируемых скрытых токенов рассуждения перед формированием финального ответа. Применение режима High Thinking для шаблонных задач форматирования кода влечет за собой избыточные задержки и финансовые траты, тогда как генерация транзакционной логики без рассуждений провоцирует критические архитектурные ошибки.

Последующие фазы кодогенерации и механического рефакторинга расходуют дешевые токены прямого вывода с минимальным скрытым мышлением.

## **Интеграция с Model Context Protocol и сетевая топология среды**

Спецификация Model Context Protocol (MCP) выступает стандартизированным транспортом взаимодействия языковой модели с локальной средой выполнения, устраняя необходимость разработки закрытых интеграционных плагинов под каждую IDE. Серверы MCP транслируют системные вызовы операционной системы, запросы к СУБД и операции Git в набор JSON-RPC функций (Tools), доступных агенту в процессе рассуждения.

Конфигурация изолирует доступ агентов по принципу наименьших привилегий: подключение к PostgreSQL ограничено правами чтения, а доступ к файловой системе разделен между базой знаний и исходным кодом.

### **Протокол доставки контекста: минимизация расхода токенов и защита внимания**

Практика передачи всей базы знаний Obsidian в контекстное окно агента при каждом запросе (Monolithic Ingestion) приводит к критическим сбоям архитектуры агентных систем:

> 1. **Размытие внимания (Attention Dilution):** Согласно исследованиям феномена «Lost in the Middle», увеличение размера контекста нерелевантной документацией снижает точность следования инструкциям до 40%. Модель начинает игнорировать критические ограничения безопасности, заложенные в системных промптах.  
> 2. **Экспоненциальный рост затрат:** Загрузка полного хранилища объемом 150 000 токенов на каждом шаге цикла TDD при 15 итерациях отладки расходует свыше 2 250 000 входных токенов на одну задачу, делая применение автономных агентов экономически убыточным.  
> 3. **Галлюцинации версионирования:** При наличии в базе знаний устаревших черновиков архитектуры модель смешивает спецификации разных этапов развития проекта.

В качестве обязательного стандарта разработки утверждается двухуровневый протокол Just-in-Time (JIT) Dynamic Context Retrieval. Агент инициирует выполнение задачи с нулевым знанием о глобальной базе документов, пошагово запрашивая точечные фрагменты через MCP-инструменты.

## **Механизм самопроверки и конвейер контроля качества**

Перевод задачи в статус ожидания рецензирования (Review) требует детерминированного подтверждения работоспособности синтезированного кода. Агенты не обладают правом субъективной оценки готовности задачи. Перед переводом метаданных в Obsidian запускается автоматический конвейер контроля качества (Quality Gate), состоящий из пяти последовательных стадий.

| Проверочный контур | Инструмент запуска через локальный шелл | Инвариант успешного прохождения (Pass Invariant) | Процедура при фиксации сбоя (Remediation Loop) |
| :---- | :---- | :---- | :---- |
| **1\. Статическая типизация** | mypy \--strict src/ | Код возврата 0\. Полное отсутствие динамических типов Any и неявных приведений. | Возврат в Medium Thinking: вывод трассировки mypy в контекст, исправление типов сигнатур. |
| **2\. Синтаксис и форматирование** | ruff check src/ tests/ && ruff format \--check | Отсутствие нарушений правил линтинга и отклонений от стиля. | Автоматический вызов агента Low Thinking для нормализации кода утилитой ruff format. |
| **3\. Контрактное соответствие** | schemathesis run 02\_Contracts/API/billing-v1.yaml \--app src.main:app | 0 непройденных проверок. Полное соответствие ответов OpenAPI-схеме. | Анализ несоответствия полей DTO агентом Medium Thinking, правка сериализатора. |
| **4\. Покрытие тестами (TDD)** | pytest \--cov=src \--cov-fail-under=90 tests/ | Код возврата 0\. Покрытие по строкам \\ge 90\\%, по ветвлениям \\ge 85\\%. | Генерация дополнительных тест-кейсов на краевые значения входных параметров. |
| **5\. Аудит дрифта базы данных** | alembic check | Отсутствие расхождений между моделями ORM, миграциями и схемой в schema.sql. | Блокировка пайплайна: статус blocked, оповещение архитектора о нарушении схемы. |

> 2. **Фаза скрытого рассуждения (Reasoning Loop):** Модель тратит \~16 000 токенов рассуждения на анализ трех механизмов изоляции: распределенная блокировка в Redis через Redlock, уровень изоляции SERIALIZABLE на транзакцию и атомарный условный апдейт UPDATE ...
