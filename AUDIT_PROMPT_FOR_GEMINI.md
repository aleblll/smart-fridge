## 🧭 1. КОНТЕКСТ И МИССИЯ ПРОЕКТА

«Умный Холодильник» (Свежесть / Svezhest) — это высоконадежное мобильное Telegram Mini App для контроля срока годности продуктов, минимизации пищевых отходов и совместного семейного ведения домашнего инвентаря.

### Ключевые возможности:
1. **Инвентаризация и зоны хранения:** Продукты распределяются по зонам: «Холодильник» (`fridge`), «Морозилка» (`freezer`), «Шкаф/кладовая» (`pantry`).
2. **Календарный расчет свежести:** Расчет остатка дней в UTC midnight без искажений локальных часовых поясов. Автоматический перевод продуктов с истекшим сроком (`daysLeft < 0`) во вкладку «Утиль» (`discarded`).
3. **Учет вскрытия упаковки:** Поддержка даты и времени вскрытия упаковки (`opened_at`) с пересчетом срока по часам/дням после вскрытия (`after_opening_hours`).
4. **Семейный шеринг:** Создание криптостойких инвайт-ссылок (`t.me/Svezhestt_bot/app?startapp=<invite_code>`) с автоматическим добавлением новых пользователей в семейный холодильник.
5. **Автономность (Thin Client + Offline Queue):** Мгновенная загрузка из `localStorage`, фоновая синхронизация с Cloudflare D1, очередь отложенных мутаций (`smart_fridge_mutation_queue`) при сбоях сети.
6. **Утренние дайджесты в Telegram:** Автоматический Cron Trigger (`0 6 * * *` = 09:00 MSK) в Cloudflare Worker, сканирующий базу D1 и рассылающий персонализированные HTML-сводки через Telegram Bot API с соблюдением рейтлимитов (25 msg/s) и отслеживанием идемпотентности.

## 🏗️ 2. АРХИТЕКТУРА И КЛЮЧЕВЫЕ КОМПОНЕНТЫ

### 2.1. Клиентская часть (`/frontend`):
- **Стек:** React 19.0, Vite 6.4, Tailwind CSS v4, `@telegram-apps/sdk-react`, `vaul` (шторки), `lucide-react`.
- **Точка входа:** [`frontend/src/main.tsx`](file:///frontend/src/main.tsx), [`frontend/src/App.tsx`](file:///frontend/src/App.tsx).
- **Контекст Telegram:** [`frontend/src/context/TelegramContext.tsx`](file:///frontend/src/context/TelegramContext.tsx) — обработка `initData`, `themeParams`, `viewport`, `requestWriteAccess`.
- **Сетевой клиент:** [`frontend/src/lib/api.ts`](file:///frontend/src/lib/api.ts) — dual-gateway fallback (`aghaskdbbb.workers.dev` primary -> `alexeyberezin2.workers.dev` fallback), передача авторизационных заголовков `X-Telegram-Init-Data` и `Authorization: tma <initData>`.
- **Локальное хранилище и кэш:** [`frontend/src/lib/storage.ts`](file:///frontend/src/lib/storage.ts) — thin client, миграция локальных данных в D1, очередь мутаций, управление несколькими холодильниками.
- **Расчет свежести:** [`frontend/src/lib/freshness.ts`](file:///frontend/src/lib/freshness.ts) — функция `calculateFreshnessMetrics`, `autoDiscardExpiredProducts`.

### 2.2. Серверная часть (`/worker`):
- **Стек:** Cloudflare Workers (TypeScript, `nodejs_compat`), Cloudflare D1 SQL Database, Cloudflare KV.
- **Точка входа:** [`worker/src/index.ts`](file:///worker/src/index.ts).
- **Схема базы данных D1:** [`worker/schema.sql`](file:///worker/schema.sql) (таблицы: `fridges`, `fridge_members`, `products`, `invites`, `user_notifications`).
- **Безопасность (Zero-Trust):** Валидация подписи HMAC-SHA256 (`WebAppData` + `bot_token`) с поддержкой Bot API 8.0, timing-safe сравнение хэшей, проверка возраста `auth_date`.
- **Cron Trigger:** Метод `scheduled` в Cloudflare Worker, запускающий рассылку дайджестов напрямую из D1.
- **Тестовый эндпоинт:** `POST /api/notify/test` — проверка доставки уведомлений пользователю в реальном времени.

### 2.3. Тестовое покрытие (`/src/__tests__`):
- Vitest монорепозитория: 39 тестов, проверяющих авторизацию воркера, CRUD продуктов, рейтлимитер, генерацию и валидацию HMAC, идемпотентность cron и пресеты продуктов.

## 🎯 3. МАКСИМАЛЬНЫЙ СПИСОК ВОПРОСОВ И ТЕМ ДЛЯ АУДИТА

### Блок A: Архитектура, Надежность и Local-First
1. **Оценка модели данных и синхронизации:** В `frontend/src/lib/storage.ts` реализована очередь мутаций в `localStorage` и миграция при несовпадении ID. Насколько эта архитектура устойчива к конкурентным изменениям, когда двое членов семьи одновременно редактируют один и тот же продукт офлайн? Какие краевые случаи приведут к потере данных (Last-Write-Wins)? Стоит ли внедрить векторные часы или CRDT?
2. **Cloudflare D1 vs KV:** Мы храним продукты в D1 SQL, а KV оставили как вспомогательный binding. Является ли D1 узким местом при резком всплеске нагрузки (например, 10 000 одновременных пользователей утром)? Каковы лимиты параллельных соединений и транзакций в D1?
3. **Dual-Gateway Fallback:** В `frontend/src/lib/api.ts` реализован автоматический fallback между поддоменами Cloudflare. Видишь ли ты скрытые риски в мутации переменной `activeBaseUrl` во время выполнения параллельных промисов?

### Блок B: Безопасность и Zero-Trust Авторизация
4. **Валидация HMAC в `worker/src/index.ts`:** Полноценно ли реализована защита от timing attacks и подделки данных? В Telegram Bot API 8.0 был добавлен параметр `signature` — насколько корректно наш код обрабатывает наличие или отсутствие этого поля?
5. **Управление жизненным циклом сессии:** Сейчас `maxAuthAge` в продакшене составляет 7 дней. Не слишком ли это много с точки зрения безопасности? Каков общепринятый стандарт времени жизни `initData` в банковских и e-commerce TMA?
6. **Безопасность семейных инвайтов:** В таблице `invites` генерируется 32-символьный hex-код, есть `max_uses: 10` и `expires_at: +7 дней`. Возможен ли DoS семейного холодильника путем исчерпания лимита инвайтов? Нужен ли рейтлимитинг на claim инвайтов на уровне IP и `user_id`?
7. **CORS и CSP заголовки:** Сейчас `worker/src/index.ts` отдает динамический Origin (`request.headers.get('Origin') || 'https://aleblll.github.io'`). Безопасно ли это, или следует вернуть строгий whitelist доменов?

### Блок C: База данных D1, SQL и Масштабируемость
8. **Индексы и структура `worker/schema.sql`:** Посмотри на схему таблиц:
   - Достаточны ли индексы `idx_products_fridge`, `idx_products_expires`, `idx_members_user`?
   - Не хватает ли составного индекса `CREATE INDEX idx_products_active_exp ON products(fridge_id, status, expires_at)` для ускорения выборки активных продуктов?
9. **Soft-Delete (`deleted_at`):** Все запросы фильтруют `deleted_at IS NULL`. Не приведет ли накопление удаленных записей через полгода к деградации производительности таблиц без партиционирования или периодического VACUUM / purge?
10. **Атомарность операций:** В роутах создания и claim инвайтов происходят множественные SQL-запросы (`first`, затем `run`). Нет ли здесь уязвимости Race Condition (Time-of-check to time-of-use), позволяющей превысить `max_uses` при параллельных запросах? Как переписать это в единую D1 Batch транзакцию?

### Блок D: Frontend, React 19, UI/UX и Рендеринг
11. **Очередь рендеринга и React 19:** Как текущие хуки `useState`, `useEffect` и `useCallback` в `App.tsx` взаимодействуют с новым компилятором React 19? Нет ли скрытых ре-рендеров всего дерева при обновлении таймеров или статусов?
12. **Размер бандла и чанкинг Vite:** В `frontend/vite.config.ts` настроен `manualChunks` для React, Telegram SDK, Vaul и Presets. Можно ли еще сильнее сократить размер `index.js` (сейчас ~83 КБ gzip: ~23 КБ) для ускорения первого старта TMA на слабых смартфонах?
13. **Отказоустойчивость кэша при обновлении версий:** Как гарантировать, что старые клиенты с закэшированным HTML в Telegram WebView гарантированно получат новые JS-ассеты без ручного «Перезагрузить страницу»?

### Блок E: Движок уведомлений и Telegram Bot API
14. **Масштабирование утренней рассылки:** Сейчас метод `scheduled` выбирает всех пользователей с истекающими продуктами и рассылает сообщения по очереди с рейтлимитом 25 msg/s. Если пользователей станет 50 000, воркер упадет по таймауту выполнения (Cloudflare Workers CPU time limit). Какую архитектуру очередей (Cloudflare Queues / Workflows / Durable Objects) ты порекомендуешь для распределенной рассылки?
15. **Логика часовых поясов:** Сейчас cron жестко настроен на `0 6 * * *` (09:00 MSK). Как правильно реализовать индивидуальное время уведомлений (например, чтобы житель Владивостока или Берлина получал дайджест в свои 09:00 утра, а не в Самарское время)?
16. **Идемпотентность и таблица `user_notifications`:** Насколько надежен текущий механизм `ON CONFLICT(user_id) DO UPDATE SET last_digest_date = excluded.last_digest_date`? Не случится ли дублирования пуша, если два триггера запустятся одновременно?
