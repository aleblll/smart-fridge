# ADR-002: Хранение справочника СанПиН/USDA в статическом бандле фронтенда

## Контекст и проблематика
Ключевая ценность приложения — добавление продукта за 3 секунды. При вводе названия пользователем («Мол...», «Сыр...») интерфейс должен мгновенно выводить подсказки с автоподстановкой категории, срока годности в днях, вторичного срока после вскрытия и рекомендаций по товарному соседству. Если выполнять поисковые запросы к внешнему API или Firebase RTDB при каждом нажатии клавиши, задержки мобильной сети (RTT 150–500 мс в сетях 3G/LTE) сделают ввод вязким, повысят расход сетевого трафика и упрутся в лимиты Firebase.

## Рассмотренные альтернативы
1. **Полнотекстовый поиск через внешний бэкенд / Serverless эндпоинт:**
   - *Плюсы:* Легкость обновления базы на сервере.
   - *Минусы:* Зависимость от сетевого соединения, сетевые задержки при автокомплите, необходимость внешнего поискового сервиса (нарушает Zero-VPS).
2. **Хранение базы пресетов в ветке Firebase RTDB `/presets`:**
   - *Плюсы:* Доступно без отдельного сервера.
   - *Минусы:* Тратит квоту скачивания Firebase (10 ГБ/мес на тарифе Spark) при каждом новом клиенте, требует сетевого запроса при холодном старте.
3. **Локальный статический JSON-файл в клиентском бандле (`src/data/foodPresets.json`):**
   - *Плюсы:* Мгновенный отклик (0 мс сетевой задержки), полная работоспособность в оффлайне, нулевая нагрузка на базу данных, эффективное сжатие Gzip/Brotli в GitHub Pages.
   - *Минусы:* Обновление базы пресетов требует повторного деплоя статического сайта.

## Решение
Утвердить хранение эталонного справочника продуктов по нормам СанПиН 2.3.2.1324-03 и USDA FoodKeeper в статическом файле `src/data/foodPresets.json` внутри клиентского бандла приложения.
- Объем оптимизированного JSON-файла для топ-300 базовых продуктов составляет ~60–80 КБ, что после Brotli-сжатия добавляет к размеру бандла всего ~15–18 КБ.
- Поиск по справочнику выполняется локально на клиенте через легковесный алгоритм префиксного сопоставления и нормализации строк (lowercase + тримминг).

## Последствия
### Положительные:
- Время отклика автокомплита составляет менее 5 мс на любых мобильных устройствах.
- Справочник доступен даже при полном отсутствии подключения к сети.
- Нулевой расход трафика и соединений в Firebase Realtime Database.
- Абсолютная детерминированность данных: тесты проверяют локальный файл напрямую.

### Отрицательные и компромиссы:
- Добавление новых нормативных позиций в базу требует коммита в репозиторий и автоматического деплоя в GitHub Pages (занимает ~1–2 минуты через GitHub Actions).
