# ADR-007: Переход на архитектуру Server-Authoritative (Cloudflare Worker + D1 SQL)

## 1. Контекст и аудит кодовой базы
По результатам детального технического ревью проекта от 2026-10-03 выявлены критические проблемы:
1. **Изоляция и потеря данных в клиенте:**
   - Фронтенд изолирован в `localStorage` и `Telegram.WebApp.CloudStorage`.
   - Лимит Telegram CloudStorage (4096 байт) приводит к тихому падению сохранения уже при 10–12 продуктах.
   - При перезапуске приложения устаревший облачный снимок затирает актуальный `localStorage`.
   - `start_param` с ID холодильника не разбирается клиентом, семейный шеринг фиктивен.
2. **Уязвимости бэкенда:**
   - Отсутствие авторизации на холодильниках: любой запрос к `GET /api/fridges/:id` создает запись в KV и отдает чужие данные.
   - Обход аутентификации: если `initData` не передана, сервер брал `userId` из тела запроса. Нет проверки возраста подписи `auth_date` (уязвимость к Replay-атакам) и timing-safe сравнения.
   - Эндпоинт `/api/cron/notify` открыт всем при пустом `CRON_SECRET`.
   - Модель KV (один JSON-блоб на холодильник) гарантирует race condition и потерю данных при параллельных правках.
3. **Логика и инфраструктура:**
   - Рассинхрон дат между UTC полночью и локальным часовым поясом (Самара UTC+4).
   - Баг в `TelegramContext`: `setIsReady(true)` недостижим из-за преждевременного `return`.
   - Утренний cron в GitHub Actions падает 10 дней подряд (отсутствие `CLOUDFLARE_WORKER_URL`), ссылка ведет на чужого бота (`SmartFridgeBot`).
   - Наличие дублей файлов (`.js` vs `.ts`, `.mjs`), отсутствие корневого `package.json`.

## 2. Принятые архитектурные решения

### Решение 1: Выбор модели «Вариант B — Сервер как источник истины»
- Источником истины становится Cloudflare Worker + реляционная БД **Cloudflare D1**.
- Фронтенд — тонкий клиент с локальным кэшем в `localStorage` / `IndexedDB` и **очередью исходящих мутаций (mutation queue)** для надежной работы офлайн.
- Ликвидация зависимости от Telegram CloudStorage как хранилища инвентаря.

### Решение 2: Модель данных в D1 (Реляционные таблицы)
Вместо одного JSON-блока в KV создаются нормализованные таблицы:
1. `fridges`: `id` (случайный криптографический UUID), `name`, `created_at`, `updated_at`.
2. `fridge_members`: `fridge_id`, `user_id`, `role` (`owner` / `member`), `joined_at`.
3. `products`: `id` (UUID), `fridge_id`, `name`, `category`, `storage_type`, `quantity` (REAL/дробное), `unit`, `opened_at`, `expires_at` (строка `YYYY-MM-DD`), `notify_before_days`, `status` (`active` / `consumed` / `discarded`), `added_by`, `created_at`, `updated_at`, `deleted_at` (Soft-delete для бесконфликтной синхронизации).
4. `invites`: `code` (криптостойкая строка 16+ байт), `fridge_id`, `created_by`, `max_uses`, `uses_count`, `expires_at`, `created_at`.

### Решение 3: Бескомпромиссная авторизация
1. `initData` обязательна для **каждого** клиентского запроса к `/api/*`. Запросы без `initData` немедленно отклоняются со статусом 401.
2. `user_id` извлекается **исключительно** из проверенного криптографического HMAC-хэша, никогда из тела запроса.
3. Проверка возраста подписи: `auth_date` не старше 3600 секунд.
4. Проверка прав на ресурс (Resource-level auth): выполнение любой операции только при наличии записи в `fridge_members`.
5. Постоянно закрытый cron: при отсутствии или несовпадении секрета возвращается 401.
6. CORS: строгий whitelist домена GitHub Pages вместо `*`.

### Решение 4: Единый калькулятор дат и сроков
- Срок годности хранится как чистая строка `YYYY-MM-DD` без часового пояса и времени.
- Все расчеты остатка дней производятся единой утилитой на основе календарной разницы дней относительно локальной даты устройства.
- Единый критерий «скоро истечет» основывается строго на поле `notify_before_days` конкретного продукта.

### Решение 5: Встроенные уведомления через Worker Cron Triggers
- Отказ от внешней рассылки через GitHub Actions.
- Использование встроенных в Cloudflare Worker `scheduled(event, env, ctx)` триггеров.
- Выборка продуктов одним SQL-запросом к D1 с учетом часовых поясов пользователей и защитой от повторной отправки (`last_digest_date`).
- Кнопка в сообщении указывает на собственный Telegram Mini App с HTTPS URL.

### Решение 6: Инфраструктурная гигиена
- Корневой `package.json` с поддержкой npm workspaces (`frontend`, `worker`).
- Единый CI-пайплайн: `lint`, `typecheck`, `test` для всех пакетов перед деплоем.
- Полное удаление дублирующихся файлов (`cloudflare-worker.js`, `notify.js`), очистка репозитория от артефактов компиляции (`.tsbuildinfo`).

## 3. План реализации по этапам
1. **Этап 1 (Клининг & Быстрые фиксы):** Корневой `package.json`, удаление дублей, исправление бага `isReady` в `TelegramContext.tsx`, единый расчет дат.
2. **Этап 2 (D1 Backend & Авторизация):** Схема D1, строгая валидация `initData` с `auth_date`, CRUD-роуты с проверкой членства.
3. **Этап 3 (Синхронизация клиента):** Подключение `storage.ts` к API, очередь мутаций, разбор `start_param` инвайтов.
4. **Этап 4 (Worker Cron Triggers):** Перенос утренних пушей внутрь воркера.
